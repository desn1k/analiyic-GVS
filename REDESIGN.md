# Карта проекта и план упрощения интерфейса

## Часть 1. Как всё устроено (что / где / откуда)

### Общая схема
```
Excel-файлы → Загрузка → Backend (FastAPI) → 2 базы SQLite → API → Frontend (React)
```
- **Backend**: `backend/app` — FastAPI, парсеры Excel, две базы.
- **Frontend**: `frontend/src` — React (Vite), таблицы и графики (recharts).
- **Deploy**: nginx отдаёт собранный фронт и проксирует `/api/*` на uvicorn (см. `DEPLOY.md`).

### Две базы данных
| База | Файл | Что хранит | Модели |
|---|---|---|---|
| Основная | `gvs.db` | недельные агрегированные отчёты | `ReportPeriod`, `TuReportRow` (`models/models.py`) |
| Приборная | `device.db` | сырые почасовые данные и справочники | `DeviceUpload`, `DevicePoint`, `DeviceHourly`, `Outage`, `ObjectRegistry`, `Hierarchy` (`models/device_models.py`) |

### Загрузка файлов (один вход, автоопределение типа)
Точка входа: `POST /api/reports/upload` (`routers/reports.py`). По содержимому файла
выбирается парсер:
| Файл | Детектор | Парсер (`services/`) | Куда |
|---|---|---|---|
| Недельный отчёт качества | по структуре | `ingest.py` → `report_parser.py` | gvs.db |
| Ведомость учёта потребления (почасовые T1/T2/V) | `looks_like_consumption_report` | `device_ingest.py` | device.db |
| Ведомость отключений | `looks_like_outage_report` | `outage_ingest.py` | device.db |
| Реестр объектов (паспорта АИИС) | `looks_like_registry` | `registry_ingest.py` | device.db |
| Иерархия (потребитель→источник) | `looks_like_hierarchy` | `hierarchy_ingest.py` | device.db |

Крупные приборные файлы парсятся в фоне (BackgroundTasks), фронт опрашивает статус
`GET /api/device/uploads/{id}`. Повторная загрузка не дублирует (INSERT OR REPLACE /
upsert по ключам). Связь между источниками — по адресу / ФИАС / object_id / tu_id
(`services/address.py` нормализует адрес).

### Эндпоинты и кто их вызывает
| Эндпоинт | Назначение | Frontend-компонент |
|---|---|---|
| `POST /api/reports/upload` | загрузка любого файла | `UploadPanel` |
| `GET /api/reports/periods` | список недель | `App` |
| `GET /api/analytics/tu` | все точки учёта (вся база) | `TuTable` |
| `GET /api/analytics/periods/{id}/tu` | точки за неделю | (резерв) |
| `GET /api/analytics/dynamics` | динамика по неделям | `DynamicsChart` |
| `GET /api/analytics/weekly-summary` | сводка по неделям | `WeeklySummaryTable` |
| `GET /api/analytics/weekly-summary/{id}/by-source` | разбивка недели по источникам | `WeekSourcesModal` |
| `GET /api/analytics/source-dynamics` | динамика источника по неделям | `WeekSourcesModal` |
| `GET /api/analytics/object-comparison` | объекты × недели | `ObjectComparisonTable` |
| `GET /api/analytics/gvs-quality` | анализ качества по приборам (СанПиН) | `GvsQualityAnalysis` |
| `GET /api/analytics/gvs-quality/export` | тот же отчёт в xlsx | `GvsQualityAnalysis` |
| `GET /api/device/points/{tu}/summary,hourly,hierarchy` | данные точки для окна | `DevicePointModal` |
| `GET /api/device/objects/{id}/outages` | отключения объекта | `DevicePointModal` |
| `GET /api/dashboard` | сводные счётчики и списки | `DashboardModal` |
| `DELETE /api/device/data` | очистка приборных данных | `DashboardModal` |

### Frontend-компоненты (что показывают)
- `App.jsx` — каркас: шапка + вертикальный список карточек-разделов.
- `UploadPanel` — кнопка загрузки + статус.
- `DashboardModal` — окно со сводкой/списками, очистка данных.
- `DynamicsChart` — график динамики по неделям.
- `WeeklySummaryTable` → `WeekSourcesModal` — сводка по неделям, клик → разбивка по источникам.
- `ObjectComparisonTable` + `FiltersBar` — сравнение объектов по неделям.
- `GvsQualityAnalysis` — анализ качества по приборам (ручной период, пороги, xlsx).
- `TuTable` → `DevicePointModal` — таблица точек, клик → окно с графиком/иерархией/отключениями.

## Часть 2. Почему интерфейс перегружен
1. **Один длинный экран** со всеми разделами сразу — новичок не понимает, с чего начать.
2. **Два источника данных** (недельный отчёт и приборы) перемешаны в одном потоке —
   похожие слова «неделя», «нарушение», «объём» значат разное.
3. **Профессиональная терминология** без пояснений (ТУ, ЦТП, ФИАС, тупиковая, СанПиН).
4. **Много таблиц с 10+ столбцами** одновременно.
5. Нет **точки входа** («что делать первым») и нет обратной связи «данных ещё нет».

## Часть 3. План упрощения (для любого возраста)

### 3.1. Экран-приветствие и «Шаг 1»
Если данных нет — большой понятный экран: «Загрузите файлы» с чек-листом 5 типов и
галочками, что уже загружено (данные берём из `/api/dashboard`). Один шаг за раз.

### 3.2. Разбить длинную страницу на 3–4 вкладки с человеческими названиями
| Вкладка | Что внутри | Для кого |
|---|---|---|
| **Данные** | загрузка + статус (что загружено, что нет) | все |
| **Качество ГВС** (главная) | анализ по приборам: период, «Показать», таблица + карта проблемных, экспорт | руководитель/инспектор |
| **Объекты** | поиск объекта → карточка с графиком, отключениями, иерархией | инженер |
| **Отчёты (недельные)** | сводка по неделям, сравнение — «продвинутое», убрать с глаз | аналитик |

### 3.3. Язык и подсказки
- Кнопки-глаголы: «Показать нарушения», «Скачать в Excel», «Открыть объект».
- Иконка «?» рядом с терминами + короткий словарь (ТУ, ЦТП, недогрев, достоверность).
- Вместо «violation_pct» — «доля часов с нарушением».

### 3.4. Мастер анализа (вместо россыпи полей)
Шаг 1 — период (пресеты: «эта неделя», «прошлая неделя»). Шаг 2 — «Показать».
Продвинутые пороги (хроническое %, достоверность %, ночь, охват) — свёрнуты под
«Дополнительно», со значениями по умолчанию.

### 3.5. Меньше видимых столбцов
Таблицы показывают 4–5 главных колонок; остальное — по кнопке «Подробнее» или в
карточке объекта. Проблемные строки подсвечены цветом, вверху — сводные плитки
(«Всего объектов», «С нарушением», «Хронических»).

### 3.6. Единая «карточка объекта»
Одно окно на объект: сверху паспорт, затем график (T + объём + зоны норматива +
отключения), ниже иерархия и история. Уже почти есть (`DevicePointModal`) — сделать
его единым местом «всё про объект».

### 3.7. Визуальная иерархия
Крупные заголовки, воздух между блоками, единая цветовая легенда (красный —
нарушение, зелёный — норма, жёлто/серый — пограничное/нет данных) во всех графиках
и таблицах.

### Порядок внедрения (по возрастанию пользы/риска)
1. Экран-приветствие + чек-лист загрузки (быстро, сразу понятнее).
2. Вкладки вместо длинной прокрутки.
3. Словарь терминов и подсказки «?».
4. Мастер анализа + сворачивание продвинутых полей.
5. Сокращение столбцов + сводные плитки.
6. Единая карточка объекта + общая цветовая легенда.

> Реализуется в отдельной ветке `claude/ui-redesign`, чтобы текущая рабочая версия
> (`claude/hydraulic-water-quality-analytics-qsog90`) не менялась и можно было
> переключаться между ними.
